# الـ Backend بتاع المتجر — شرح كامل من الصفر

الملف ده هيشرحلك كل حاجة عملتها، وليه، وإزاي تشغّلها، حتى لو أول مرة تتعامل مع backend.

---

## 1) الصورة الكبيرة الأول

أي موقع بيتكون من 3 حاجات بتتكلم مع بعض:

```
[المتصفح / الموقع (Angular)]  <-->  [الـ Backend (Server)]  <-->  [قاعدة البيانات]
        الفرونت إند                    Express.js                  SQLite
```

- **الفرونت إند (اللي عملناه قبل كده بـ Angular)**: هو اللي المستخدم بيشوفه ويتعامل معاه (الأزرار، الصفحات، التصميم).
- **الـ Backend**: برنامج شغال على السيرفر، شغلته إنه يستقبل طلبات من الموقع (زي "هاتلي كل المنتجات" أو "احفظلي الطلب ده")، يتكلم مع قاعدة البيانات، ويرجع النتيجة.
- **قاعدة البيانات (Database)**: مكان تخزين دائم للبيانات (المنتجات، الطلبات، حساب الأدمن)، بحيث البيانات متفضلش موجودة في المتصفح بس وتضيع لو مسحت الكاش.

قبل كده، الموقع كان بيحفظ كل حاجة في `localStorage` بتاع المتصفح — يعني كل جهاز/متصفح له بياناته الخاصة، ومفيش حد تاني (زبون تاني، أو انت من موبايلك) يقدر يشوف نفس البيانات. دلوقتي بقى فيه **مصدر واحد حقيقي للبيانات** (قاعدة البيانات) يقدر يوصله أي حد بيفتح الموقع.

---

## 2) قاعدة البيانات (Database) اللي عملتها

استخدمت **SQLite** — وهي قاعدة بيانات حقيقية (بتفهم لغة SQL زي أي قاعدة بيانات احترافية) لكنها كلها موجودة في **ملف واحد** على جهازك (`data/store.sqlite`)، مفيهاش تعقيد تثبيت سيرفر قاعدة بيانات منفصل. مناسبة جداً للبداية، ولمشروع بالحجم ده هتفضل شغالة كويس حتى لو كبر شوية.

> ملحوظة تقنية: بنستخدم `node:sqlite` وهي مكتبة SQLite **مدمجة جوه Node.js نفسه** (من إصدار 22.5 فما فوق) —
> مش مكتبة خارجية محتاجة تثبيت أو Compiler (زي Python أو Visual Studio Build Tools). يعني
> `npm install` هيشتغل من غير أي مشاكل تثبيت على أي جهاز (ويندوز/ماك/لينكس) طول ما عندك
> Node.js حديث.

### الجداول (Tables) اللي فيها:

| الجدول | بيخزن إيه |
|---|---|
| `products` | كل منتج: الاسم، السعر، التصنيف، الوحدة، متوفر ولا لأ... إلخ |
| `orders` | كل طلب: بيانات العميل، الإجمالي، الحالة (قيد الانتظار/مؤكد/...) |
| `order_items` | تفاصيل المنتجات جوه كل طلب (كل صنف وكميته وسعره وقت الطلب) |
| `settings` | اسم المتجر ورقم الواتساب (صف واحد بس، بتتعدل من الإعدادات) |
| `admin_users` | حساب الأدمن (اسم المستخدم + كلمة المرور **مُشفّرة**، مش نص عادي) |

أول ما تشغّل السيرفر لأول مرة، بيعمل الجداول دي تلقائياً، وبيحط فيها بيانات تجريبية (نفس الـ 14 منتج اللي كانوا في الموقع)، وبيعمل حساب أدمن افتراضي. المرات اللي بعد كده مش بيلمس البيانات (عشان أي تعديل تعمله يفضل محفوظ).

**الملف اللي بيعمل كل ده**: `src/db.js`

## 3) الـ Authentication (تسجيل الدخول) — إزاي بيشتغل بالظبط

قبل كده، كلمة سر الأدمن (`admin123`) كانت **مكتوبة صراحة جوه كود الفرونت إند**، يعني أي حد يفتح "عرض الصفحة/View Source" في المتصفح يقدر يشوفها ويدخل لوحة التحكم من غير أي مشكلة — ده مش آمن خالص.

دلوقتي بقى في نظام تسجيل دخول حقيقي، وده اللي بيحصل خطوة بخطوة:

1. **كلمة السر متخزنة مُشفّرة (Hashed)، مش زي ما هي**: باستخدام مكتبة `bcrypt`. يعني حتى لو حد قدر يفتح قاعدة البيانات نفسها، مش هيقدر يعرف كلمة السر الحقيقية — بس يقدر يتأكد إن كلمة سر معينة "صح ولا لأ" وقت تسجيل الدخول.

2. **عملية تسجيل الدخول**:
   - المستخدم بيكتب كلمة السر في صفحة الأدمن.
   - الموقع بيبعتها لل backend على `POST /api/auth/login`.
   - الـ backend بيقارن كلمة السر دي بالنسخة المشفّرة المخزنة.
   - لو مطابقة: بيرجع **JWT Token** (شويه أحرف وأرقام طويلة، زي توقيع رقمي مؤقت يثبت "أنت مسجل دخولك").
   - الموقع بيحفظ التوكن ده في المتصفح.

3. **بعد كده، أي طلب "حساس"** (زي: احذف منتج، عدّل طلب، شوف كل الطلبات) الموقع بيبعت التوكن ده مع الطلب في الـ header:
   ```
   Authorization: Bearer <التوكن>
   ```
   والـ backend بيتأكد إن التوكن ده صحيح وماإتغيرش قبل ما ينفذ أي حاجة. لو مفيش توكن أو غلط، بيرفض الطلب برسالة **401 Unauthorized**.

4. **التوكن بينتهي بعد مدة** (7 أيام افتراضياً، تقدر تغيّرها)، فبعدها المستخدم لازم يسجّل دخول تاني — ده طبيعي وأأمن من توكن يفضل شغال للأبد.

**الملفات المسؤولة عن ده**:
- `src/routes/auth.routes.js` — استقبال تسجيل الدخول وإصدار التوكن
- `src/middleware/auth.js` — التحقق من التوكن قبل أي مسار محمي

> ملحوظة مهمة: غيّر `JWT_SECRET` و `ADMIN_PASSWORD` في ملف `.env` قبل ما ترفع الموقع لأي حد يشوفه فعلياً (شرح تحت).

## 4) الـ API (الطلبات اللي الموقع بيبعتها للـ backend)

| الطريقة | المسار | محمي بتسجيل دخول؟ | الوظيفة |
|---|---|---|---|
| GET | `/api/products` | لا | جلب كل المنتجات |
| POST | `/api/products` | نعم | إضافة منتج جديد |
| PUT | `/api/products/:id` | نعم | تعديل منتج |
| DELETE | `/api/products/:id` | نعم | حذف منتج |
| GET | `/api/orders` | نعم | جلب كل الطلبات (لوحة التحكم) |
| POST | `/api/orders` | لا | إرسال طلب جديد (Checkout) |
| PATCH | `/api/orders/:id/status` | نعم | تغيير حالة الطلب |
| GET | `/api/settings` | لا | جلب اسم المتجر ورقم الواتساب |
| PUT | `/api/settings` | نعم | تعديل الإعدادات |
| POST | `/api/auth/login` | لا | تسجيل الدخول |
| GET | `/api/auth/me` | نعم | التأكد إن جلسة الدخول لسه صالحة |

**ليه بعض المسارات مش محمية؟** لإن أي زبون عادي (مش أدمن) لازم يقدر يتصفح المنتجات ويعمل طلب من غير ما يكون عنده حساب — ده طبيعي في أي متجر إلكتروني.

**نقطة أمان مهمة**: لما حد يعمل طلب (checkout)، الـ backend **بيحسب السعر بنفسه من قاعدة البيانات**، مش بياخد السعر اللي جاله من المتصفح. ده بيمنع حد "شاطر" من التلاعب بالكود وتغيير السعر قبل ما يبعت الطلب.

## 5) إزاي اتربط بالموقع (الفرونت إند)

عملت في مشروع Angular:
- `src/app/services/api.service.ts` — فيه كل دوال الاتصال بالـ backend (جلب المنتجات، تسجيل الدخول، إلخ)
- `src/app/services/auth.service.ts` — بيحفظ التوكن وبيدير حالة "مسجل دخول ولا لأ"
- `src/app/services/store.service.ts` — بقى بيجيب البيانات من الـ backend بدل ما كانت متخزنة في المتصفح بس

يعني دلوقتي أي حد يفتح الموقع من أي جهاز، هيشوف نفس المنتجات ونفس الإعدادات، ولو الأدمن ضاف منتج من عنده، هيظهر لكل الزباين على طول.

## 6) إزاي تشغّل كل حاجة

### الخطوة 1: شغّل الـ Backend الأول

```bash
cd store-app-backend
npm install
cp .env.example .env
npm start
```

هتشوف في الآخر:
```
✅ Backend API شغال على http://localhost:4000
```

سيبه شغال في نافذة Terminal.

### الخطوة 2: شغّل الفرونت إند (Angular) في نافذة تانية

```bash
cd store-app-angular
npm install
ng serve -o
```

هيفتحلك الموقع على `http://localhost:4200` وهيبدأ يجيب البيانات من الـ backend تلقائياً.

### تسجيل دخول الأدمن

- روح لوحة التحكم من الموقع
- كلمة السر: اللي حطيتها انت في ملف `.env` بتاع الـ backend (متغيّر `ADMIN_PASSWORD`) — **مش مكتوبة في أي ملف تاني في المشروع ولا في أي مكان تاني عشان تفضل سرية**. لو غيّرت كلمة السر في `.env` بعد أول تشغيل، احذف ملف `data/store.sqlite` وشغّل السيرفر تاني عشان يتعمل حساب الأدمن من جديد بكلمة السر الجديدة.

## 7) لما تيجي ترفع الموقع فعلياً (Production) — حاجات مهمة

1. **غيّر `JWT_SECRET`** في `.env` لنص عشوائي طويل (مثلاً 40+ حرف/رقم عشوائي).
2. **غيّر `ADMIN_PASSWORD`** لكلمة سر قوية.
3. **غيّر `FRONTEND_URL`** في `.env` بتاع الـ backend لدومين موقعك الحقيقي (بدل `localhost:4200`).
4. **غيّر `apiUrl`** في `store-app-angular/src/environments/environment.ts` لعنوان الـ backend بعد ما ترفعه (مثلاً `https://api.mystore.com/api`).
5. لازم الـ backend يكون شغال على سيرفر حقيقي (مش جهازك)، زي: Render, Railway, DigitalOcean, VPS عادي بأي مزوّد. لو محتاج مساعدة في الرفع، قولّي هنعملها خطوة بخطوة.

## 9) مشاكل شائعة (Troubleshooting)

**"Cannot find module..." أو أي خطأ بعد `npm install`**
اتأكد إنك بتشغّل `npm install` وانت **جوه فولدر `store-app-backend`** بالظبط (مش الفولدر اللي فيه المشروعين الاتنين).

**السيرفر بيقولك JWT_SECRET مش موجود**
معناها نسيت تعمل نسخة من `.env.example` باسم `.env` (الخطوة 4 فوق).

**عندك Node.js قديم (أقل من 22.5)**
السيرفر هيديك رسالة واضحة تقولك كده. حدّث Node.js من [nodejs.org](https://nodejs.org)
(نزّل نسخة LTS) وجرب تاني.

**الموقع (Angular) بيقول "تعذّر الاتصال بالسيرفر"**
يبقى الـ backend مش شغال، أو قافل قبل ما تفتح الموقع. ارجع لنافذة الـ backend وشوف هل
لسه شغالة وطابعة `✅ Backend API شغال على http://localhost:4000`.

## 10) خلاصة بسيطة جداً لو نسيت كل التفاصيل

- الموقع (Angular) = **الشكل اللي الناس بتشوفه**.
- الـ Backend (Node.js + Express) = **العقل اللي بيحسب ويتحقق ويحمي البيانات**.
- الـ Database (SQLite) = **الخزنة اللي البيانات بتتخزن فيها فعلياً**.
- الـ JWT Token = **تذكرة دخول مؤقتة** بتثبت إنك سجّلت دخولك كأدمن، من غير ما تبعت كلمة السر في كل طلب.

أي حاجة مش واضحة أو عايز تتعمق فيها أكتر، قولّي وهشرحهالك بالتفصيل.
